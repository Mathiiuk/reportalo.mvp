### Pruebas ejecutadas el 2026-10-04 (autorizadas por Matías)

**Prueba 1 · SQL con rollback** (`DO` con `set local role authenticated` + claims del usuario QA, terminado en `raise exception` para revertir; verificado después: 0 filas de prueba, 212 reportes en total):

| Caso | Resultado |
| --- | --- |
| A · `INSERT … ON CONFLICT (client_side_id) DO UPDATE` con `client_side_id` **nuevo** | `OK` |
| B · el mismo `INSERT` con el `client_side_id` de un reporte **ya creado** | `ERROR 42501: new row violates row-level security policy (USING expression) for table "citizen_reports"` |

**Prueba 2 · desde la app, con la sesión de Matías** (`createCitizenReport` real, `client_side_id` de un reporte propio ya existente, mismos datos, sin cambios en la base):

```
success: false
userMessage: "No pudimos guardar tu reporte. Tu borrador sigue guardado: probá de nuevo en unos segundos."
technical: { message: 'new row violates row-level security policy (USING expression) for table "citizen_reports"', code: '42501', details: null, hint: null, status: 403 }
```

**Conclusión:** el alta con un `client_side_id` nuevo funciona y con uno ya existente falla **siempre** con 42501/403 (no hay policy UPDATE), con el mismo mensaje genérico que vio QA. El comentario de `NewReportPage.jsx` («el envío de la cola recupera ese mismo reporte») es falso hoy: la recuperación idempotente nunca funcionó. Además queda confirmado que el motivo técnico ahora se ve.

**Lo que sigue sin confirmarse:** por qué, a las 01:08 y 01:27, el `client_side_id` ya existía (las filas de esos intentos no están en la base). El escenario más probable es el alta que sí llega al servidor pero cuya respuesta se pierde (timeout `SEND_TIMED_OUT` → `saveForLaterAndExit`), con lo que el reintento desde la cola cae siempre en UPDATE. No se reprodujo de punta a punta.
