# Specification — REP-2204

Jira: https://unlz2026.atlassian.net/browse/REP-2204 (HU · épica REP-1002 Flujo de reporte ciudadano · Sprint 13)

## 1. Objetivo

Que el ciudadano pueda enviar el reporte con una acción clara, solo cuando están los datos mínimos, sin duplicarlo
por un doble toque, y con una falla que no le haga perder lo que cargó.

## 2. Problema actual (medido contra el código de `staging` `2f34a70`)

| Criterio de la HU | Hallazgo |
|---|---|
| Botón solo con datos mínimos | El botón «Enviar reporte» nunca se deshabilitaba: solo se controlaba la localidad. No revisaba foto, categoría ni descripción. |
| Solo evidencia sanitizada, categoría, descripción y ubicación | **Con las categorías de respaldo (sin conexión o consulta fallida) el reporte se guardaba con `service_id = null`, sin categoría y sin avisar.** La cola offline tenía el mismo problema. |
| Sin doble envío | `isSubmittingReport` se escribía pero nadie lo leía. Un segundo toque repetía el registro de consentimiento; sin conexión, el guardado y el aviso. |
| Éxito con identificador | Ya existe (`formatReportCode` + pantalla «Reporte enviado»). Se verifica con test. |
| Fallo sin perder datos | El flujo vuelve a la revisión con el borrador intacto, pero **mostraba el mensaje crudo de Supabase** al ciudadano. |
| La imagen original nunca se transmite | Ya garantizado: `isServerProtectedUrl` corta el envío si alguna foto no salió protegida del servidor (H-30) y el alta solo manda URLs del bucket de evidencias. |

## 3. Resultado esperado

Ver criterios de aceptación (§5).

## 4. Alcance

### Incluido
- `reportReadiness.js`: regla única de datos mínimos y de qué falta.
- Botón de envío: `aria-disabled`, atenuado, con la lista de lo que falta y «Enviando…» durante el envío.
- Candado contra el doble envío (ref síncrono) y segunda barrera en la persistencia.
- `resolveServiceDbId`: resuelve la categoría por `service_code` al enviar (en línea y en la cola offline).
- `createCitizenReport` devuelve `userMessage` y no lanza ante una excepción de red.

### No incluido
- Cambios en la pantalla de éxito ni en el pipeline de anonimización (REP-2501, REP-2400).
- Reintento automático del envío en línea.

## 5. Criterios de aceptación

- [x] AC-01: datos incompletos → botón no disponible y con el motivo a la vista
- [x] AC-02: sin ubicación confirmada el botón sigue abriendo el ajuste de ubicación
- [x] AC-03: durante el envío muestra «Enviando…» y no reacciona
- [x] AC-04: dos toques → un solo registro de consentimiento y un solo reporte
- [x] AC-05: categoría resuelta al enviar; si no se puede, no se envía sin categoría
- [x] AC-06: error comprensible que aclara que el borrador sigue guardado
- [x] AC-07: tests de éxito, validación y fallo
- [ ] Smoke manual en el `staging` desplegado

## 6. Restricciones

- **Decisión de diseño**: el botón usa `aria-disabled` y no `disabled`, para que siga enfocable y, sin localidad confirmada, conserve el comportamiento de abrir el ajuste de ubicación (R-1/R-2, tests UT-RV-00 y UT-EVD-08).
- Rama desde `staging`; `main` no se toca.

## 7. Dependencias

REP-2203 (descripción 10–280), REP-2500 (persistencia), REP-2501 (evidencia protegida), REP-2703 (borrador offline).

## 8. Riesgos

- Si la tabla `services` no responde al enviar y la categoría no trae `dbId`, el envío se detiene con un aviso (antes se guardaba sin categoría). Es el comportamiento buscado, pero puede verse como «más estricto».
- El test `UT-OFF-FLOW-01` es intermitente bajo carga (falla en frío y pasa al repetir); no lo modifica esta tarea.
