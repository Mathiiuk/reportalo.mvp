# Specification — REP-2908

## 1. Objetivo

Reemplazar el spike de RAG jurídico de REP-2907 por una implementación que cumpla la promesa real de un RAG: toda cita normativa sale exclusivamente del corpus verificado precargado, la búsqueda es por significado real (no por palabras clave hechas a mano) y el texto de fundamento lo redacta un LLM, nunca reglas de negocio hardcodeadas.

## 2. Problema actual

`src/services/legalRagService.js` (REP-2907) no es un RAG real:

- `INITIAL_LEGAL_CORPUS` es un array de 8 fragmentos **hardcodeado en JS**, no filas de una base de datos cargadas desde un corpus versionado.
- `generateDeterministicEmbedding` no es un embedding: es un **matching de raíces léxicas en español armado a mano** (buckets semánticos fijos de 64 dimensiones + hashing de respaldo). Fue señalado explícitamente como inválido para medir calidad de recuperación real en `docs/REP-2907_handoff_para_agente.md` punto 3, porque se ajustó a mano contra los mismos casos con los que se mide (100% de acierto autoengañoso).
- No hay ningún paso de LLM: no se redacta `fundamento_ciudadano`/`fundamento_oficial`, no se analiza contenido de imagen. El pipeline de cuarentena (`supabase/functions/quarantine-anonymize`) solo hace privacidad (EXIF + blur de rostros/patentes vía Google Vision), no tiene relación con la fundamentación jurídica.
- La cascada jurisdiccional se resuelve con `resolveEligibleJurisdictions`, que hace matching de texto sobre el string de jurisdicción — no con la cadena geográfica real (`localities → subdivisions → states_provinces → countries`) ni con `source_adhesions`.

## 3. Resultado esperado

Un pipeline donde:

1. El corpus vive en tablas (`knowledge_sources`, `knowledge_fragments`, `source_adhesions`, `fragment_embeddings`), cargado desde los `.md` verificados de `docs/fuentes/normativas/` — nunca hardcodeado en el código de aplicación ni re-scrapeado en tiempo de consulta.
2. Los vectores son reales, calculados por `gemini-embedding-2` a 768 dimensiones, tanto para los fragmentos del corpus como para el texto de cada reporte.
3. La cascada jurisdiccional (municipio → provincia/CABA → nación, con adhesiones) se resuelve en SQL server-side vía el RPC `match_knowledge_fragments`, según la consulta documentada en `docs/REP-1009_RAG_de_punta_a_punta.docx` §4.3.
4. Si ningún fragmento supera el umbral de similitud, no se llama al LLM (`sin_normativa`, cero riesgo de invención).
5. Si hay fragmentos elegibles, un LLM (`gemini-3.8-flash`) redacta el fundamento citando textualmente solo lo recuperado, con salida en esquema JSON obligatorio.
6. El código valida de forma determinística (sin confiar en el LLM) que cada `fragment_id` citado esté entre los recuperados y que cada `cita_textual` aparezca literalmente en el fragmento. Ante cualquier fallo: `indeterminado`, nunca un resultado de reemplazo inventado.

## 4. Alcance

### Incluido

- Reescritura de `src/services/legalRagService.js` (o su reemplazo) para que la recuperación pase por una interfaz de embeddings + una llamada al RPC `match_knowledge_fragments`, con un cliente de embeddings/LLM inyectable y mockeable para tests.
- Migración SQL (nueva o reutilizando `docs/REP-3769_seed_y_RAG.sql` como referencia) que define el esquema `knowledge_*` y el RPC de búsqueda con cascada, versionada en `supabase/`.
- Edge Function `analizar-reporte` (Deno) que implementa los pasos 4 a 10 del flujo del docx §5: vectorizar, recuperar, umbral, llamar al LLM, validar, persistir.
- Validación determinística de la respuesta del LLM (esquema, fragment_id, cita literal, organismo existente).
- Suite de tests (Vitest) que reproduce los casos A–F de `docs/REP-3764_casos_esperados.md` contra el nuevo pipeline, con un doble de prueba (fake) para el cliente de Gemini/embeddings — sin llamadas de red reales.

### No incluido (fuera de esta tarea, por decisión explícita de Matías dado el entorno de esta sesión)

- Ejecutar la migración SQL contra un proyecto Supabase real (no hay Supabase CLI ni credenciales de servicio en este entorno).
- Configurar los secrets de Gemini en Supabase ni hacer llamadas reales a la API de Gemini.
- Habilitar las extensiones `pgmq`, `pg_cron`, `pg_net` en un proyecto real, ni desplegar la Edge Function.
- Cargar el corpus real en la base (eso es la ejecución de `REP-3769_seed_y_RAG.sql`, responsabilidad de Hernán/Matías fuera de esta sesión).
- Decisiones abiertas del docx §12 que exceden el código (R-2 adhesión CABA/Ley 24.449, R-6 índice único parcial) — se documentan como pendientes, no se resuelven acá.

## 5. Criterios de aceptación

- [ ] AC-01: sin `INITIAL_LEGAL_CORPUS` ni `generateDeterministicEmbedding` en el código de producción.
- [ ] AC-02: migración SQL versionada con el esquema `knowledge_*` y el RPC `match_knowledge_fragments`.
- [ ] AC-03: Edge Function `analizar-reporte` con el cliente Gemini detrás de una interfaz inyectable.
- [ ] AC-04: validación determinística que fuerza `indeterminado` ante cualquier incumplimiento de esquema/cita/organismo.
- [ ] AC-05: tests de los 6 casos A–F con doble de prueba determinístico, sin red.
- [ ] AC-06: `pnpm test` en verde; ninguna ejecución real contra Supabase/Gemini desde esta tarea.

## 6. Restricciones

- Nada hardcodeado: ni corpus, ni URLs de fuentes normativas usadas como fundamento en tiempo de ejecución, ni reglas de clasificación por palabra clave que reemplacen al LLM.
- Nada resuelto por internet en tiempo de consulta: el corpus se carga una vez, versionado; el pipeline de consulta nunca hace fetch a una fuente externa para fundamentar un reporte.
- Fallar cerrado siempre: ante cualquier ambigüedad, error de validación o fallo de umbral, el resultado es `indeterminado` o `sin_normativa`, nunca una respuesta de reemplazo inventada.
- No tocar el pipeline de privacidad/cuarentena (`quarantinePipelineService.js`, `quarantine-anonymize`) — es un sistema aparte y ya validado en Sprint 11.

## 8. Riesgos

- Sin acceso real a Gemini en este entorno, la validación de calidad de embeddings/generación no puede probarse end-to-end aquí — solo con el doble de prueba. Matías/Hernán deben correr la primera validación real fuera de esta sesión.
- El esquema de `REP-3769_seed_y_RAG.sql` puede tener ajustes pendientes (R-6: índice único parcial) que no bloquean el código de aplicación pero sí la migración real.
- Sin Supabase CLI, no se puede confirmar que el RPC compile/ejecute correctamente contra Postgres real desde esta sesión — solo revisión estática del SQL.
