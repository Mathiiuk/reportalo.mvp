## 1. Estrategia

El diseño ya viene especificado y verificado por UX en REP-3791, así que no corresponde
regenerar spec/plan/feature por bloque. Se corre el ciclo completo una vez a nivel de ticket
y cada bloque se trata como una unidad de entrega:

```
rama desde staging → git apply del .patch → quality gates → evidencia → PR (lo abre Matías)
```

Los bloques llegan de a uno. No se acumulan ni se aplican en lote.

## 2. Convención: una rama, un commit por bloque

**Una sola rama para todo el ticket: `feat/REP-3787-uj33`**, derivada de `staging`. Cada bloque
entra como un commit propio sobre esa rama:

```
feat(ui): REP-3787 UJ v3.3 bloque 0 — fundaciones de color, tipografia y accesibilidad
feat(ui): REP-3787 UJ v3.3 bloque 1 — nuevo reporte mobile (M09, M10, M12)
feat(ui): REP-3787 UJ v3.3 bloque 1-D — nuevo reporte escritorio (D10, D11, D13)
...
```

### Por qué no una rama por bloque

Los bloques **no son independientes**: el Bloque 0 define los tokens de color y la escala
tipográfica que usan todos los demás. Verificado el 21/09/2026: el parche del Bloque 1 tiene
**166 referencias** a clases `rep-*` y `cat-*` que solo existen si el Bloque 0 ya está aplicado
(`rep-accent`, `rep-surface`, `text-rep-label`, `rep-focus`, entre otras).

Si se mergearan como PR separados y el Bloque 1 entrara primero, Tailwind no generaría esas
clases y M09, M10 y M12 quedarían sin estilos. El LEEME del handoff ya proponía encadenar los
bloques; la propuesta es correcta y se adopta.

Un commit por bloque conserva lo que se buscaba con las ramas —poder revisar, revertir o
bisecar bloque por bloque— sin el riesgo de que se mergeen desordenados, y sin obligar a abrir
un PR por cada uno.

### PR

Un solo PR de `feat/REP-3787-uj33` contra `staging`. Se puede abrir apenas hay un bloque útil
y seguir sumando commits: el PR se actualiza solo con cada push. **El push y el PR los hace
Matías**, el agente no ejecuta `git push`.

Si un bloque resulta problemático, se revierte su commit sin tocar los demás.
## 3. Procedimiento por bloque

1. Estar en `feat/REP-3787-uj33`, con el bloque anterior ya commiteado.
2. `git apply --check -v <bloque>.patch` — si hay conflicto, **no** forzar: pedir a Ivo que
   regenere el bloque contra staging actual.
3. `git apply <bloque>.patch`
4. Revisar el `README.md` del bloque y contrastar contra las capturas.
5. Quality gates: `pnpm test` y `pnpm build`.
6. Comparar contra la baseline (§4). Cualquier fallo nuevo se corrige antes de seguir.
7. Commit semántico: `feat(ui): REP-3787 UJ v3.3 bloque <N> — <funcionalidad>`
8. Reporte de ejecución en `.agents/workflow/executions/REP-3787-bloque-<N>.md`.
9. **Push y PR: los hace Matías.** El agente no ejecuta `git push`. El PR es uno solo para todo el ticket y se actualiza con cada push.
