# Implementation Plan — REP-2500

## 1. Resumen

Reemplazar el envío de reporte "mock" (solo avanza pasos de UI, borra el borrador local, muestra un código hardcodeado) por un envío real: insert en `citizen_reports`, copia de la evidencia ya sanitizada al bucket definitivo `report-evidences` + insert en `report_images`, manejo de fallo sin informar éxito falso, y `ReportsPage.jsx` leyendo datos reales en vez de `demoReports`.

## 2. Repositorio inspeccionado

- Stack: React/Vite, Supabase (Postgres + Storage + Edge Functions), Zustand/IndexedDB para borradores offline.
- Runtime: navegador (PWA offline-first).
- Package manager: pnpm.
- Branch base: `staging` (rama de esta tarea: `feat/REP-2500-conservar-el-reporte-enviado-para-consultarlo-despues`).
- Hallazgos de la investigación previa (sin código, solo lectura) ya resumidos en la spec §2.

**Verificado contra Supabase real (solo lectura, vía MCP) antes de planificar:**
- `report_states`: `RECIBIDO` es el código correcto para "estado inicial" de un envío confirmado (existen también `EN_ANALISIS`, `DERIVADO`, `RESUELTO`, `DESESTIMADO`).
- Bucket de Storage `report-evidences`: **ya existe**, es público, con políticas de `INSERT`/`SELECT`/`UPDATE`/`DELETE` ya creadas (`bucket_id = 'report-evidences'`, sin restricción de owner). No hace falta crear infraestructura de Storage.
- `citizen_reports`: RLS ya permite `INSERT`/`SELECT` públicos (`insert_publico`, `lectura_publica`) — el cliente ya puede escribir ahí tal como está.
- **`report_images`: RLS habilitado, CERO políticas.** Hoy nadie puede leer ni escribir esa tabla pese a que existe y tiene FK correcta a `citizen_reports`. Esto bloquea todo el flujo de evidencia — es un prerrequisito, no un detalle.
- `categoriesService.js` ya expone `selectedCategory.dbId` = `services.id` real — el mapeo categoría→`service_id` ya existe, no hay que construirlo.

## 3. Cambios propuestos

### [NEW]
- `src/services/reportSubmissionService.js` — servicio nuevo, aislado, con la lógica pura de: `createCitizenReport({ userId, serviceId, localityId, description, latitud, longitud })` (insert en `citizen_reports`, retorna `{ data, error }`) y `attachReportEvidence({ reportId, sanitizedFile })` (copia el archivo sanitizado al bucket `report-evidences` bajo una key determinística tipo `${reportId}/${uuid}.jpg`, luego insert en `report_images`). Funciones puras/testeables con Vitest, siguiendo el patrón ya usado en `reportAiAnalysisPersistence.js`.

### [MODIFY]
- `src/pages/NewReportPage.jsx` — `handleSubmitReport`: en el camino online, después de `goToStep(4)` (procesamiento de evidencia), al terminar el pipeline de cuarentena exitosamente, llamar a `createCitizenReport` y luego `attachReportEvidence` con el resultado sanitizado. Si cualquiera de los dos falla, NO avanzar a la pantalla de éxito (paso 6) — mostrar error y **no borrar** el borrador local (`deleteDraftReport` se mueve a después de la confirmación exitosa, no antes).
- `src/components/report/ReportProcessingScreen.jsx` — el pipeline ya orquesta la sanitización de evidencia; se extiende para, al finalizar, invocar la persistencia real (o exponer un callback que `NewReportPage` use para encadenar `createCitizenReport`/`attachReportEvidence`).
- `src/components/report/ReportSuccessScreen.jsx` — quitar el `reportCode="#RP-2048"` hardcodeado; recibir el `id`/`client_side_id` real del reporte persistido como prop.
- `src/pages/ReportsPage.jsx` — reemplazar `demoReports` como fuente por defecto: nuevo `useEffect` que llama a un `getMyReports(userId)` (nuevo, en `reportSubmissionService.js` o un servicio de lectura separado) filtrando `citizen_reports` por `user_id`. Mantener el modo demo como toggle explícito si ya existe esa UX, pero que el estado real (no vacío por falta de fetch) sea el default.

### [SQL — requiere autorización antes de aplicar]
- Políticas RLS para `report_images` (hoy sin ninguna): `INSERT` público con `with_check` atado a que exista el `citizen_reports.id` referenciado (o más simple, público sin restricción adicional, igual que `citizen_reports`), y `SELECT` público (los reportes ya son públicos por diseño, la evidencia sanitizada también debería serlo). Se documenta el SQL exacto antes de aplicarlo contra Supabase real, con el mismo patrón de "pido OK antes de cada acción irreversible" de toda la sesión.

## 4. Estrategia de implementación

1. Escribir `reportSubmissionService.js` con las funciones puras (`createCitizenReport`, `attachReportEvidence`, `getMyReports`) + tests Vitest con un cliente Supabase mockeado (mismo patrón que `ReportAiAnalysisPersistence.test.js`).
2. **Pedir OK explícito y aplicar** la política RLS faltante en `report_images` contra Supabase real (bloqueante: sin esto, ningún insert de evidencia va a funcionar, ni siquiera en pruebas manuales).
3. Conectar `NewReportPage.jsx`/`ReportProcessingScreen.jsx` a los nuevos servicios, invirtiendo el orden actual: persistir primero, avanzar a "éxito" solo si se confirma.
4. Actualizar `ReportSuccessScreen.jsx` para mostrar el identificador real.
5. Conectar `ReportsPage.jsx` a `getMyReports`.
6. Actualizar/agregar tests: `NewReportFlow.test.jsx`, `ReportPostSubmissionFlow.test.jsx` van a necesitar mockear el nuevo servicio en vez de solo props; agregar un test nuevo que verifique explícitamente que un fallo de persistencia NO llega a la pantalla de éxito (AC-05).
7. `pnpm test` completo + `pnpm run build`.
8. Verificación manual en el navegador: crear un reporte real de punta a punta contra Supabase real (con tu autorización, dado que escribe en la base real) y confirmar que aparece en "mis reportes".

## 5. Migraciones / datos

- Política RLS de `report_images` (única migración necesaria, ver §3 SQL). No se prevén cambios de esquema (columnas/tablas) — el modelo de datos ya está listo.

## 6. Seguridad

- Verificar que el `with_check` del insert de `report_images` no permita adjuntar evidencia a un `report_id` ajeno de forma arbitraria sin sentido (aunque el modelo actual es público por diseño, conviene que al menos el `report_id` referenciado exista — la FK ya lo garantiza a nivel de integridad).
- No se sube nunca la foto original ni el resultado con EXIF — se reusa el pipeline de cuarentena ya probado tal cual, solo se agrega el paso de copia final del resultado ya sanitizado.

## 7. Observabilidad

- Loggear (consola, como el resto del código de la app) cualquier fallo de `createCitizenReport`/`attachReportEvidence` con detalle suficiente para diagnosticar sin exponer datos sensibles al usuario final.

## 8. Compatibilidad / rollback

- Cambio de comportamiento puro en frontend + una política RLS aditiva (no destructiva) — reversible: si algo sale mal, se puede revertir el PR y/o borrar la política sin efecto en datos existentes.
- No afecta el flujo offline existente (Sprint 11): los borradores `PENDING_SYNC` siguen funcionando igual: esta HU solo cambia qué pasa cuando el envío es online.

- `ReportsPage.jsx` muestra los reportes reales del ciudadano.
- Tests en verde, build limpio.
