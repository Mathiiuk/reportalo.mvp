# Implementation Plan — REP-2500

## 1. Resumen

Reemplazar el envío de reporte "mock" (solo avanza pasos de UI, borra el borrador local, muestra un código hardcodeado) por un envío real: insert en `citizen_reports`, copia de la evidencia ya sanitizada al bucket definitivo `report-evidences` + insert en `report_images`, manejo de fallo sin informar éxito falso, y `ReportsPage.jsx` leyendo datos reales en vez de `demoReports`.

## 2. Repositorio inspeccionado

- Stack: React/Vite, Supabase (Postgres + Storage + Edge Functions), Zustand/IndexedDB para borradores offline.
- Runtime: navegador (PWA offline-first).
- Package manager: pnpm.
- Branch base: `staging` (rama de esta tarea: `feat/REP-2500-conservar-el-reporte-enviado-para-consultarlo-despues`).
- Hallazgos de la investigación previa (sin código, solo lectura) ya resumidos en la spec §2.

**Verificado contra Supabase real (solo lectura, vía MCP) antes de planificar:**
- `report_states`: `RECIBIDO` es el código correcto para "estado inicial" de un envío confirmado (existen también `EN_ANALISIS`, `DERIVADO`, `RESUELTO`, `DESESTIMADO`).
- Bucket de Storage `report-evidences`: **ya existe**, es público, con políticas de `INSERT`/`SELECT`/`UPDATE`/`DELETE` ya creadas (`bucket_id = 'report-evidences'`, sin restricción de owner). No hace falta crear infraestructura de Storage.
- `citizen_reports`: RLS ya permite `INSERT`/`SELECT` públicos (`insert_publico`, `lectura_publica`) — el cliente ya puede escribir ahí tal como está.
- **`report_images`: ya tiene políticas públicas** (`insert_publico`/`lectura_publica`, aplicadas el 14/09 como parte de la verificación del RAG — migración `20260914205949_add_rls_policies_report_images.sql`). Ya no es un bloqueante.
- `categoriesService.js` ya expone `selectedCategory.dbId` = `services.id` real — el mapeo categoría→`service_id` ya existe, no hay que construirlo.

**Decisión del PO sobre `locality_id` (REP-2908-VERIF_ronda2_hernan.md §4, 15/09):**
- **Se aprueba la Opción 1** (selector manual de localidad) para cerrar REP-2500 en Sprint 12. La geolocalización automática (reverse-geocoding) queda como deuda técnica, HU aparte — no se construye acá.
- El "duplicado de Avellaneda" en `localities` **no es un error**: son dos lugares reales distintos (partido de Avellaneda, Buenos Aires vs. departamento Avellaneda, Santa Fe), cargados a propósito para probar que el sistema nunca resuelve una localidad solo por nombre. Consecuencia directa: el selector **siempre** guarda `locality_id` (el UUID elegido), nunca busca por texto.
- **Requisitos del selector (R-1 a R-5):**
  - R-1: cada opción se muestra como `"Localidad — Partido/Comuna, Provincia"` (ej. `"Avellaneda — Avellaneda, Buenos Aires"`), para distinguir localidades homónimas.
  - R-2: la lista se limita a la zona piloto: barrios de CABA + localidades del partido de Avellaneda (Buenos Aires). Santa Fe no aparece — filtrar por `states_provinces.name = 'Ciudad Autónoma de Buenos Aires'` o (`subdivisions.name = 'Avellaneda'` y `states_provinces.name = 'Buenos Aires'`).
  - R-3: el texto del campo pregunta por la ubicación del problema, no de quien reporta (ej. "¿En qué barrio o localidad está el problema?").
  - R-4: junto al selector se muestra el pin del mapa con la ubicación real del GPS, para que el ciudadano pueda comparar.
  - R-5: autocompletado mientras se escribe, sin distinguir tildes (ej. "pineyro" encuentra "Piñeyro") — son ~56 opciones, necesita búsqueda.
- **Correcciones que entran con REP-2500, no son deuda (E-1 a E-4):**
  - E-1: quitar la calle inventada de `resolveAddressDetails()` (ej. "Av. Mitre 1240"). Mostrar el pin y las coordenadas, o nada.
  - E-2: borrar el borrador local (`deleteDraftReport`) solo cuando el servidor confirma que guardó el reporte, no al llegar a la pantalla de éxito.
  - E-3: si se reintenta un envío, usar el mismo `client_side_id` — ante conflicto (`UNIQUE`), recuperar el reporte existente en vez de mostrar error (idempotencia offline, ADR-009).
  - E-4: la pantalla de éxito muestra el código real del reporte guardado, no el hardcode `"#RP-2048"`.
- **Criterios de aceptación para QA (4.5 del documento de Hernán):**
  1. Un reporte enviado queda en `citizen_reports` con el `locality_id` elegido, y dispara el análisis del RAG (se ve en `report_ai_analysis`).
  2. Elegir "Avellaneda — Avellaneda, Buenos Aires" guarda el `id` de Buenos Aires, nunca el de Santa Fe.
  3. Un reporte armado sin conexión se guarda una sola vez al recuperar la conexión, aunque se reintente.
  4. Si el envío falla, el borrador sigue en el dispositivo.
  5. En ninguna pantalla aparece una calle inventada.

## 4. Estrategia de implementación

1. Escribir `localitiesService.js` (`getSelectableLocalities`) + `LocalitySelector.jsx` (R-1 a R-5) + tests.
2. Escribir `reportSubmissionService.js` con las funciones puras (`createCitizenReport`, `attachReportEvidence`, `getMyReports`) + tests Vitest con un cliente Supabase mockeado (mismo patrón que `ReportAiAnalysisPersistence.test.js`). `createCitizenReport` idempotente por `client_side_id` (E-3).
3. E-1: sacar la calle inventada de `locationService.js`. Integrar `LocalitySelector` en `AdjustLocationModal.jsx` (R-4: junto al pin).
4. Conectar `NewReportPage.jsx` a los nuevos servicios, invirtiendo el orden actual: persistir primero, avanzar a "éxito" solo si se confirma. E-2: mover `deleteDraftReport` a después de la confirmación.
5. E-4: actualizar `ReportSuccessScreen.jsx` para mostrar el identificador real.
6. Conectar `ReportsPage.jsx` a `getMyReports`.
7. Actualizar/agregar tests: `NewReportFlow.test.jsx`, `ReportPostSubmissionFlow.test.jsx` van a necesitar mockear el nuevo servicio en vez de solo props; agregar un test nuevo que verifique explícitamente que un fallo de persistencia NO llega a la pantalla de éxito (AC-05), y uno para el reintento idempotente (E-3/AC-03 de 4.5).
8. `pnpm test` completo + `pnpm run build`.
9. Verificación manual en el navegador: crear un reporte real de punta a punta contra Supabase real (con tu autorización) y confirmar que aparece en "mis reportes" y dispara el análisis del RAG (criterio 1 de 4.5).

## 5. Migraciones / datos

- Ninguna. La política RLS de `report_images` ya está aplicada (14/09). El modelo de datos ya está listo, incluida la zona piloto de `localities`.

## 6. Seguridad

- Verificar que el `with_check` del insert de `report_images` no permita adjuntar evidencia a un `report_id` ajeno de forma arbitraria sin sentido (aunque el modelo actual es público por diseño, conviene que al menos el `report_id` referenciado exista — la FK ya lo garantiza a nivel de integridad).
- No se sube nunca la foto original ni el resultado con EXIF — se reusa el pipeline de cuarentena ya probado tal cual, solo se agrega el paso de copia final del resultado ya sanitizado.

## 7. Observabilidad

- Loggear (consola, como el resto del código de la app) cualquier fallo de `createCitizenReport`/`attachReportEvidence` con detalle suficiente para diagnosticar sin exponer datos sensibles al usuario final.

## 8. Compatibilidad / rollback

- Cambio de comportamiento puro en frontend + una política RLS aditiva (no destructiva) — reversible: si algo sale mal, se puede revertir el PR y/o borrar la política sin efecto en datos existentes.
- No afecta el flujo offline existente (Sprint 11): los borradores `PENDING_SYNC` siguen funcionando igual: esta HU solo cambia qué pasa cuando el envío es online.

## 10. Definition of Done

- Un envío online real crea `citizen_reports` + `report_images` en Supabase, sin foto original ni EXIF.
- La pantalla de éxito muestra el ID real, no un hardcode.
- Un fallo de persistencia no llega nunca a la pantalla de éxito, y no borra el borrador local.
- `ReportsPage.jsx` muestra los reportes reales del ciudadano.
- Tests en verde, build limpio.
