# Implementation Plan — REP-2909

## 1. Resumen

Cuatro bloques que conectan el motor RAG (REP-2908) con el mundo real: disparo automático, guardado del resultado, permisos de lectura, y una pantalla que lo muestre. Se implementan como código/SQL versionado; la ejecución contra Supabase real requiere autorización explícita de Matías en el momento, igual que en REP-2908.

## 2. Repositorio inspeccionado

- Stack: igual que REP-2908 (Vite + React 18 + Supabase + Vitest).
- Rama base: `staging` (rama de trabajo: `feat/REP-2909-cerrar-rag-productivo-...`).
- Depende directamente de los archivos que dejó REP-2908: `legalRagService.js`, `geminiClient.js`, `analizar-reporte/index.ts`, `rag_knowledge_schema.sql`.

## 3. Cambios propuestos

### [NEW]
- `supabase/rag_async_pipeline.sql` — trigger en `citizen_reports` + tabla/cola `pgmq` + job `pg_cron` + llamada `pg_net` a `analizar-reporte`. Comentado paso a paso, con orden de aplicación relativo a `docs/REP-3769_seed_y_RAG.sql`.
- `supabase/rag_rls_policies.sql` — políticas RLS de `report_ai_analysis` y `report_ai_evidence` (bloque 3), aisladas en su propio archivo para que Matías las revise por separado (son las más sensibles de seguridad).
- `src/components/report/ReportAiAnalysisPanel.jsx` — componente que renderiza el estado del análisis (5 estados posibles) en el detalle del reporte.
- `src/test/ReportAiAnalysisPanel.test.jsx` — tests del componente en sus 5 estados, con datos fixture.
- `src/services/reportAiAnalysisService.js` (o similar) — función que trae el análisis de un reporte desde Supabase (lectura, respeta RLS) para que la consuma el componente.

### [MODIFY]
- `supabase/functions/analizar-reporte/index.ts` — agregar el paso de persistencia (bloque 2) al final del flujo, dentro de una transacción, con el borrado del mensaje de cola condicionado al éxito de la escritura.
- La pantalla de detalle de reporte existente (a identificar exactamente cuál — revisar `src/pages/ReportsPage.jsx` y componentes de detalle) para incorporar `ReportAiAnalysisPanel`.

## 4. Estrategia de implementación

1. Bloque 1 (SQL, sin dependencias de código): escribir el trigger + cola + cron siguiendo el patrón "Automatic embeddings" de Supabase citado en el docx, con comentarios explicando cada paso.
2. Bloque 2 (Edge Function): extender `analizar-reporte` con la escritura transaccional. Como no hay Supabase real disponible, se revisa estáticamente y se agrega un test de la lógica de armado del payload de persistencia (separando "construir las filas a insertar" de "ejecutar el insert", para que la primera parte sea testeable sin base real).
3. Bloque 3 (RLS): escribir las políticas calcando el criterio ya usado en `citizen_reports`, documentando explícitamente qué se verificó a mano (no hay forma de correr un test de RLS real sin Supabase).
4. Bloque 4 (frontend): construir el componente contra datos fixture primero (mismos 5 estados: fundamentado, indeterminado, sin_normativa, fuera_de_alcance, asistencia), después el service de lectura real — que devuelve `null`/vacío con gracia si `report_ai_analysis` no existe todavía en el entorno (para no romper la pantalla en local/staging mientras el resto no esté desplegado).

## 5. Migraciones / datos

- `rag_async_pipeline.sql` y `rag_rls_policies.sql`: escritos, no ejecutados sin autorización explícita en el momento.

## 6. Seguridad

- Bloque 3 es el más sensible: revisar con cuidado que la política no exponga análisis de reportes ajenos. Documentar el criterio exacto y pedir revisión de Matías antes de aplicar en real.

## 7. Observabilidad

- El log de la Edge Function (ya definido en REP-2908) debe incluir si la persistencia tuvo éxito o no, para poder diagnosticar mensajes de cola que quedan reintentando.

## 8. Compatibilidad / rollback

- El trigger/cola/cron se puede deshabilitar sin tocar el resto del sistema (no rompe `citizen_reports` si se remueve).
- El componente de frontend debe degradar con gracia (no mostrar nada, no romper la pantalla) si `report_ai_analysis` no tiene fila para ese reporte.
