# Specification — REP-3309

## 1. Objetivo

Auditar y reforzar la seguridad del sistema de autenticación de Reportalo V2 contra los patrones de `auth-implementation-patterns` y `security-guardian`, protegiendo tokens, sesiones y OAuth.

## 2. Problema actual

La autenticación tenía múltiples vulnerabilidades según los estándares de seguridad:
- **Tokens en localStorage**: Supabase almacena tokens en localStorage por defecto, vulnerable a XSS
- **Logout incompleto**: `signOut()` solo seteaba null en estado local, no invalidaba tokens en servidor ni limpiaba localStorage
- **Sin validación de redirect URLs**: OAuth `redirectTo` usaba `window.location.origin` directo sin whitelist (vulnerable a open redirect)
- **Tokens en URL**: Después del callback OAuth, tokens podían quedar expuestos en hash fragments
- **Sin security headers**: No había headers de protección HTTP (CSP, X-Frame-Options, etc.)
- **Sin auditoría de eventos**: No se loggeaban eventos de login/logout

## 3. Resultado esperado

Sistema de autenticación que cumpla con:
- Zero Trust: validar todo, no confiar en el cliente
- Defense in depth: múltiples capas de protección
- Secure by design: seguridad desde el diseño, no después

## 4. Alcance

### Incluido
- Configuración de Supabase con PKCE flow
- Whitelist de dominios para redirect OAuth
- Login con Google usando redirect validado + prompt:select_account
- Logout global con invalidación de todos los refresh tokens
- Limpieza de tokens residuales de localStorage
- Limpieza de tokens de la URL después de callbacks
- Security headers HTTP (X-Content-Type-Options, X-Frame-Options, etc.)
- Logging de eventos de autenticación

### No incluido
- Rate limiting en backend (requiere configuración de Supabase)
- MFA (Multi-Factor Authentication)
- RBAC (Role-Based Access Control)
- Refresh token rotativo (gestionado por Supabase internamente)

## 5. Criterios de aceptación

- [x] AC-01: Supabase client configurado con PKCE flow
- [x] AC-02: Whitelist de dominios permitidos para redirect OAuth
- [x] AC-03: signInWithGoogle usa getSecureRedirectUrl() validado
- [x] AC-04: signInWithGoogle configura prompt=select_account
- [x] AC-05: signOut usa scope='global'
- [x] AC-06: signOut limpia tokens residuales de localStorage
- [x] AC-07: signOut en AuthContext usa try/finally
- [x] AC-08: cleanOAuthCallbackUrl() limpia tokens de la URL
- [x] AC-09: AuthContext llama cleanOAuthCallbackUrl al montar y después de SIGNED_IN
- [x] AC-10: Logging de eventos de auth
- [x] AC-11-15: Security headers en vercel.json

## 6. Restricciones

- No se puede modificar el comportamiento interno de Supabase SDK
- Las cookies HttpOnly son gestionadas por Supabase, no por la app
- Mantener compatibilidad con Google OAuth

## 7. Dependencias

- @supabase/supabase-js ^2.49
- Google OAuth configurado en Supabase Dashboard
- Vercel deployment

## 8. Riesgos

- `scope='global'` en signOut cierra sesión en TODOS los dispositivos del usuario (comportamiento intencional)
- PKCE flow puede no ser soportado por todos los proveedores OAuth (Google sí lo soporta)

## 9. Impacto

### Frontend
- 3 archivos modificados: supabase.js, authService.js, AuthContext.jsx

### Backend
- Sin cambios (Supabase gestiona el backend)

### Database
- Sin cambios

### Infraestructura
- vercel.json: 5 security headers agregados

### Seguridad
- Tokens protegidos contra XSS via PKCE
- Redirect URLs validadas contra open redirect
- Logout inválida tokens en servidor + limpia localStorage
- Tokens limpiados de URL después de OAuth
- Headers HTTP protegen contra clickjacking, sniffing, XSS
