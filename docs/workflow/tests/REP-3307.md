# Test Plan — REP-3307: Configurar Ambiente Staging

## 1. Objetivo de las Pruebas

Verificar que la rama `staging` dispare las validaciones automáticas de CI y Seguridad, que Vercel actualice el dominio fijo de Staging y que el Sponsor (**Carlos Ruiz**) pueda acceder permanentemente al entorno.

## 2. Casos de Prueba

### TC-01: Validación de Sintaxis YAML de Workflows
- **Objetivo**: Asegurar que `ci.yml` y `security.yml` tengan sintaxis válida con la lista de ramas `[main, staging]`.
- **Resultado Esperado**: Validación PyYAML exitosa sin errores de parseo.

### TC-02: Creación y Publicación de la Rama `staging`
- **Objetivo**: Confirmar que la rama `staging` existe localmente y en el repositorio remoto de GitHub.
- **Resultado Esperado**: `git branch -a` muestra `staging` y `origin/staging`.

### TC-03: Ejecución de Pipelines en Push a `staging`
- **Objetivo**: Verificar que al hacer push o merge a `staging`, GitHub Actions dispare los jobs `quality` y `security`.
- **Resultado Esperado**: Ambos workflows concluyen con status verde en GitHub Actions.

### TC-04: Asignación de Dominio Fijo en Vercel
- **Objetivo**: Comprobar que el dominio `reportalo-staging.vercel.app` (o similar) esté configurado con `Git Branch: staging`.
- **Resultado Esperado**: Al acceder a la URL de Staging, se visualiza el build correspondiente al último commit de la rama `staging`.

### TC-05: Acceso del Sponsor (Carlos Ruiz)
- **Objetivo**: Abrir la URL fija de Staging desde un navegador en incógnito o sin cuenta en Vercel.
- **Resultado Esperado**: La página carga inmediatamente sin solicitar credenciales ni permisos de Vercel.
